# Async Export Job pipeline, run from a separate standalone Worker

Every server-side Render (customer Export, Admin Publish validation, admin scripts) goes through the same async pipeline: a request creates an Export Job row in D1 (`queued`), sends a message to a Cloudflare Queue, a Queue consumer picks it up, routes it to a Cloudflare Container running native OpenSCAD, writes the resulting STL to R2, and updates the job to `done`/`failed`. The caller polls `GET /api/jobs/:id` until it settles. We considered a synchronous model instead — the Worker holds the HTTP request open and proxies straight to a Container — which is simpler (no job table, no polling), but renders can run well past a minute (we measured ~90s for a genuinely complex template), which is too long to comfortably hold a single connection open across mobile networks and intermediate proxies, and a burst of concurrent exports has no natural queuing under that model — they'd all hit containers at once. The async model decouples the request's lifecycle from the render's, gives Export Jobs a natural home for retries and caching (identical Template-version + Configuration requests reuse a prior job's result), and lets queue depth absorb bursts instead of dropping them.

**This pipeline had to become its own standalone Worker project (`render-worker/`), separate from the Pages project the rest of the app is deployed as** — not a preference, a hard platform constraint discovered while building it: Cloudflare Containers and Queue consumers are not available to Pages Functions, only to plain Workers (Pages Functions can still be a Queue *producer*, which is all the main app needs). The two projects share the same D1 database and R2 bucket — Cloudflare resources aren't project-exclusive — so this is a deployment-topology split, not a data or architecture split: the main Pages project creates and polls Export Jobs; `render-worker/` is the only thing that ever moves one from `queued` to `done`. Revisiting this — collapsing back into one deployable — would mean migrating the whole app off Pages onto Workers-with-assets (Cloudflare's own stated direction for Pages generally), which is a real option later but out of scope for adding this one feature.
