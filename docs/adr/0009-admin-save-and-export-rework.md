# Save no longer validates before persisting; Render moves to two on-demand buttons; Admin gets its own STL/3MF Export

The Admin's "Publish" action — which blocked on both the client-side and server-side engines successfully Rendering the draft before persisting anything (ADR-0002, ADR-0005) — is renamed "Save" and no longer does that check. Save is now pure metadata persistence: it writes whatever's in the form (name, description, source, Template Manifest, Listed state) to D1, whether or not the source currently renders on either engine. An Admin can now Save a Template that's actively broken, and if it's Listed, that's what customers see. This is a deliberate trade of the previous safety net for speed and flexibility — accepted knowingly, not overlooked, on the reasoning that the Admin is a single trusted actor who can already preview both engines on demand (see below) and is in the best position to judge when a half-finished draft is worth saving anyway.

In its place, "Render (browser)" and "Render (server)" are now two always-visible buttons in the Admin Panel, available regardless of whether `estimateComplexity` flags the Template expensive — previously, a manual server Render was only offered as a fallback for Templates too expensive to auto-render client-side. The Admin can now check either engine, any time, independent of Saving. Whichever was clicked most recently is what the Viewer shows; a Configuration change reverts the Viewer to the client-side engine's own (typically already-current, since it auto-renders unless skipped) result, since a stale server Render from before the change would be misleading to keep showing.

Admin also gets its own Export, distinct from a customer's: a format dropdown (STL or 3MF — OpenSCAD's own 3MF export only exists server-side, since the vendored `openscad-wasm` build has lib3mf compiled out, confirmed by a string literal in the binary itself saying so), and no Account gate, since Admin auth already covers it. Routing: STL reuses the browser's already-rendered Mesh instantly via `three`'s `STLExporter` when one exists — no Container round-trip — falling back to a fresh server-side Export Job only when there's no client Render to reuse or when 3MF was chosen. This is a genuinely different mechanism from the customer Export Job flow (which is always server-side, always STL, always Account-gated) sharing only the underlying Export Job table and Container pipeline where the server path is actually used.
