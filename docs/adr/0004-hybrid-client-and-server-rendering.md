# Hybrid rendering: server-side only for Export and Admin Publish, not the interactive preview

Server-side rendering (native OpenSCAD in a Cloudflare Container) was added to handle render workload at scale — but only for Export and Admin Publish validation, not the Customize view's or Admin Panel's live preview, which both stay exactly as ADR-0001/ADR-0002 already established: client-side, in a Web Worker, through openscad-wasm.

This matters because "how many customers are rendering concurrently" barely applies to the interactive preview: rendering there already scales for free — each customer's own browser does its own compute, so 100 customers moving sliders at once costs the infrastructure nothing extra. Moving *that* server-side would mean every slider drag becomes a network round-trip through a queue, competing for shared container capacity, for no benefit — instant client-side feedback is strictly better UX and free. The actual scaling question only exists for Export (and, by extension, the identical server-side check Admin Publish needs — see ADR-0002's own reasoning about the Admin getting the same experience as end users, now extended to a second, server-side check): a customer clicking Export is a deliberate, occasional action, not a continuous stream, so sizing container capacity for bursts of *exports* — not for every interactive tweak from every customer — is the right unit of scale to design around.

The cost of this split: two rendering engines (WASM vs. native OpenSCAD) now need to be kept in sync — see the parity discipline already established when server-side rendering was designed (matching fonts between the two, documented alongside CONTEXT.md's Render and Export Job entries) — rather than one.
