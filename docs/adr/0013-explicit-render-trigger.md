# Customer Configuration changes require an explicit Render click

The customer-facing Customize view no longer re-renders on every Configuration change. The first Render for a Template still fires automatically (so the default-preview cache from [ADR-0010](./0010-cached-default-preview.md) keeps paying off on first paint), but any Parameter change after that just marks the current Mesh stale — a "Parameters have changed — click Render to update" hint appears, the old Mesh stays on screen, and nothing actually re-renders until the customer clicks the new Render button. `useRenderMesh` gained a `requireManualTrigger` flag and a `render()` function for this; the Admin Panel's own live preview is untouched (still auto-renders on every change, per [ADR-0009](./0009-admin-save-and-export-rework.md)'s reasoning that an Admin always wants a current result). _That Admin exception was later reversed. See [ADR-0015](./0015-admin-render-is-explicit-too.md)._

This is a different reason than [ADR-0007](./0007-skip-then-server-fallback-for-expensive-preview.md)'s retired skip-gate ([ADR-0012](./0012-remove-customer-skip-gate.md)) — that one was about not hanging the tab on a Template estimated too expensive to auto-render, and `useRenderMesh`'s 60s timeout still guards against that regardless of trigger model. This change is about not re-rendering *at all* on every slider tick, for every Template, expensive or not — investigating why [Bambu Lab's MakerWorld Parametric Model Maker](https://makerworld.com/en/makerlab/parametricModelMaker?pageType=generator) feels fast (see `docs/research/makerworld-parametric-generator-speed.md`) found it uses exactly this pattern: an explicit "Generate" click, never a live render per parameter edit — batching an arbitrary number of edits into one deliberate request instead of firing (and frequently discarding) one per keystroke.

Applies uniformly to every Template, not just ones `estimateComplexity` flags expensive — ADR-0012 removed the "some Templates behave differently than others" gate for exactly the confusion that caused, and reintroducing that split here (simple Templates keep auto-rendering, complex ones don't) would risk the same failure mode in a new form. The button is labeled "Render," not "Generate" — this project already has a precisely-defined Render term (CONTEXT.md, with its own `_Avoid_` list), and the button does exactly that action manually instead of automatically; introducing a second word for the same concept would fight that existing discipline for no real benefit.
