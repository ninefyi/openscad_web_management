# render-worker Container sized for a ~100-concurrent-render burst

`render-worker`'s Container moved from `instance_type = "lite"` (1/16 vCPU, 256 MiB) to `standard-2` (1 vCPU, 6 GiB), and `max_instances` from 5 to 25 — sized for a burst of roughly 100 concurrent render requests (customer Export, Admin Render on server/Export, default-preview warm jobs — see ADR-0010), scoped to the worst case already observed in this Template library rather than the common case: a Minkowski-heavy Template took 80-120s on `lite` in production. A synthetic equivalent run locally showed real, if sub-linear, CPU contention once concurrent renders on a machine approached its core count (13.5s → 51s going from 1 to 8 concurrent on an 8-core test host) — this is a *throughput* result (how many jobs a given amount of total CPU can get through per unit time when many run at once), not a claim that any single job gets faster with more vCPU allocated to it.

That distinction mattered enough to verify directly rather than assume: after deploying `standard-2`, the same Minkowski-heavy Template was re-run through Admin's Render on server in production and took ~120-127s — essentially unchanged from `lite`'s 80-120s, despite 16x more allocated vCPU. **The tier upgrade does not make an individual heavy render faster.** The likely reason is that OpenSCAD's Minkowski implementation (via CGAL/Manifold) is predominantly single-core-bound for a given job regardless of how much vCPU the Container is allocated — the earlier concurrency test measured something different (many *separate* jobs sharing a CPU pool, where more total cores lets more of them proceed without contention), and conflating the two would have been a real mistake in this record. This project has no evidence, from either the earlier ADRs or its own vendored image, that OpenSCAD's boolean/Minkowski evaluation is meaningfully parallelizable within one job.

What this capacity change actually buys, and the only thing it was ever really justified by, is **concurrency headroom, not per-job speed**: `lite`'s tiny fractional vCPU meant only a handful of renders could run at once before contending hard with each other; `standard-2` at `max_instances = 25` means a burst of concurrent requests — the ~100-request target this was sized against — clears through 25 parallel Containers instead of 5, each taking roughly the same wall-clock time per job as before. Queueing a burst rather than requiring every one of the 100 to start simultaneously remains the deliberate choice it always was (the existing `render-jobs` Queue, `max_batch_size = 1`, already shapes this as queue-and-process, not real-time, and customers/Admins already see "In queue…" during normal operation) — 25 instances just means more of the queue drains in parallel per round. Cloudflare Containers has no documented ceiling anywhere near 100 concurrent instances on a Workers Paid account (account-wide pool: 1,500 concurrent vCPU), so the real constraint was always this project's own `max_instances`, not the platform.

No hard spend cap exists on Cloudflare for Workers Paid/Containers usage — confirmed directly from their own billing docs ("Budget alerts are informational only. They do not pause or cap usage."). `max_instances` is therefore the actual cost governor here: it bounds worst-case concurrent resource draw, and therefore worst-case spend *rate*, even though it says nothing about total monthly spend (that's driven by actual usage volume, which is expected to be far below this burst ceiling most of the time). A Cloudflare Budget Alert (dashboard: Manage Account → Billing → Billable Usage) is set as a secondary, informational safety net, not a substitute for this.
