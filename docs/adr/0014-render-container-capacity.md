# render-worker Container sized for a ~100-concurrent-render burst

`render-worker`'s Container moved from `instance_type = "lite"` (1/16 vCPU, 256 MiB) to `standard-2` (1 vCPU, 6 GiB), and `max_instances` from 5 to 25 — sized for a burst of roughly 100 concurrent render requests (customer Export, Admin Render on server/Export, default-preview warm jobs — see ADR-0010), scoped to the worst case already observed in this Template library rather than the common case: a Minkowski-heavy Template took 80-120s on `lite` in production, and a synthetic equivalent showed real, if sub-linear, CPU contention once concurrent renders on a machine approached its core count (13.5s → 51s going from 1 to 8 concurrent on an 8-core test host). `lite`'s fractional vCPU was a reasonable fit for the light Templates this library started with; it isn't for one this heavy, especially many of them at once.

Queueing a burst rather than requiring every one of the 100 to start simultaneously was an explicit, deliberate choice — the existing `render-jobs` Queue (`max_batch_size = 1`) already shapes this as a queue-and-process system, not a real-time one, and customers/Admins already see "In queue…" during normal operation. 25 instances clears a 100-job burst in a handful of queued rounds rather than one Container at a time, without provisioning for the (much more expensive, and per Cloudflare's own documented account-wide resource pools, unnecessary) case of all 100 running at once — Cloudflare Containers has no documented ceiling anywhere near 100 concurrent instances on a Workers Paid account (account-wide pool: 1,500 concurrent vCPU), so the real constraint was always this project's own `max_instances`, not the platform.

No hard spend cap exists on Cloudflare for Workers Paid/Containers usage — confirmed directly from their own billing docs ("Budget alerts are informational only. They do not pause or cap usage."). `max_instances` is therefore the actual cost governor here: it bounds worst-case concurrent resource draw, and therefore worst-case spend *rate*, even though it says nothing about total monthly spend (that's driven by actual usage volume, which is expected to be far below this burst ceiling most of the time). A Cloudflare Budget Alert (dashboard: Manage Account → Billing → Billable Usage) is set as a secondary, informational safety net, not a substitute for this.
