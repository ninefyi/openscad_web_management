# render-worker Container sized for a ~100-concurrent-render burst, on standard-4

`render-worker`'s Container runs `instance_type = "standard-4"` (4 vCPU, 12 GiB, 20 GB disk), `max_instances = 25` — sized for a burst of roughly 100 concurrent render requests (customer Export, Admin Render on server/Export, default-preview warm jobs — see ADR-0010), scoped to the worst case already observed in this Template library rather than the common case: a Minkowski-heavy Template took 80-120s on the original `lite` tier (1/16 vCPU) in production. Getting here took two real deploys and a wrong turn worth recording, because the wrong turn is exactly the kind of thing a future reader would otherwise repeat.

**First attempt, `standard-2` (1 vCPU) — no improvement, and initially misread.** A synthetic concurrency test run locally (13.5s → 51s going from 1 to 8 concurrent renders on an 8-core host) showed real throughput scaling and was initially taken as a hint that more vCPU would also speed up a *single* heavy render. It doesn't: re-running the same Minkowski-heavy Template on `standard-2` in production took ~120-127s — essentially unchanged from `lite`, despite 16x more allocated vCPU. The concurrency test measured something different (many separate jobs sharing a CPU pool) and conflating the two was a real mistake, corrected in this ADR's own history rather than left standing.

**Why `standard-2` didn't help, and `standard-4` does — confirmed, not guessed.** OpenSCAD's build compiles Manifold with TBB-based multi-threading forced on (`openscad/openscad`'s `CMakeLists.txt` sets `MANIFOLD_PAR ON` whenever Manifold is enabled) — threading was never compiled out. The actual reason: TBB parallelism needs **at least two physical cores** to produce any wall-clock speedup, and `standard-2`'s "1 vCPU" is exactly one core — going from a throttled 1/16 core (`lite`) to an un-throttled but still-single 1 core (`standard-2`) is still "one core" as far as TBB is concerned. Deploying `standard-4` (4 real cores) and re-running the identical Template on Admin's Render on server took **~18s** — roughly 7x faster than `standard-2`, verified directly in production (fresh job id, real network round-trip, correct geometry rendered) rather than assumed from the CPU-core theory alone.

This also means the capacity change now buys **both** concurrency headroom and per-job speed, not concurrency alone as an earlier version of this ADR concluded once `standard-2` was all that had been tried: `max_instances = 25` still clears a burst of ~100 concurrent requests through 25 parallel Containers, and each of those Containers now finishes a worst-case render in ~18s instead of ~120s. It's also not a cost/speed trade-off — 4 vCPU × 18s (≈72 vCPU-seconds) is *less* total compute than 1 vCPU × ~124s (≈124 vCPU-seconds) on `standard-2`, because the speedup outpaces the larger allocation. Queueing a burst rather than requiring every one of the 100 to start simultaneously remains the deliberate choice it always was (the existing `render-jobs` Queue, `max_batch_size = 1`, already shapes this as queue-and-process, not real-time). Cloudflare Containers has no documented ceiling anywhere near 100 concurrent instances on a Workers Paid account (account-wide pool: 1,500 concurrent vCPU), so the real constraint was always this project's own `max_instances`, not the platform.

**Where this still won't help.** TBB parallelizes convex-operand Minkowski and general boolean ops; for *concave* operands, OpenSCAD's Manifold-backed Minkowski path still falls back to CGAL's Nef-polyhedron machinery, and upstream issue `openscad/openscad#6297` documents that conversion step as "terribly slow" independent of core count. This project's own worst-case Template happened to still benefit substantially from more cores, but a future Template whose slowness comes from that specific CGAL fallback path, not from single-core-bound TBB work, may not respond the same way to a bigger tier — worth re-verifying empirically (the way this ADR did) rather than assuming the ~7x number generalizes.

No hard spend cap exists on Cloudflare for Workers Paid/Containers usage — confirmed directly from their own billing docs ("Budget alerts are informational only. They do not pause or cap usage."). `max_instances` is therefore the actual cost governor here: it bounds worst-case concurrent resource draw, and therefore worst-case spend *rate*, even though it says nothing about total monthly spend (that's driven by actual usage volume, which is expected to be far below this burst ceiling most of the time, and — per the finding above — is now cheaper per worst-case job than the smaller tier was). A Cloudflare Budget Alert (dashboard: Manage Account → Billing → Billable Usage) is set as a secondary, informational safety net, not a substitute for this.
